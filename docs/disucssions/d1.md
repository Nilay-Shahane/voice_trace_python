Answers are written the way you'd actually say them — understand the reasoning, don't recite.

## Project overview

**Explain VoiceTrace in 60 seconds.**
A voice-first financial copilot for street vendors. A vendor speaks a sentence like "sold 2 samosas for 30 rupees," it's transcribed via a dual-pass Whisper pipeline, passed to a LangGraph agent that classifies the transaction type, validates completeness, and either extracts a structured record into MongoDB or asks a catalog-grounded clarifying question. Streamed to the frontend over SSE so the user sees progress live. Built with FastAPI on the backend. Placed Top 12 at ColoHacks.

**What problem were you trying to solve?**
Street vendors don't have time or comfort to fill forms between customers — typing, especially in a non-native script, is real friction. Voice is the lowest-friction way to capture a transaction at the moment it happens, which is also when it's most accurate.

**What exactly was your role in the project?**
I built the entire backend: the FastAPI server, the dual-Whisper transcription pipeline, the LangGraph orchestration (all nodes, schemas, routing logic), MongoDB integration, SSE streaming, checkpointed memory, and LangSmith observability wiring.

**What technologies did you personally implement?**
FastAPI, LangGraph (StateGraph, conditional edges, MemorySaver checkpointing), OpenAI Whisper (dual pipeline), Pydantic structured-output schemas, Motor (async MongoDB), SSE streaming, LangSmith tracing.

**Walk me through the complete flow from user audio to database entry.**
1. Audio uploaded to `/api/speech_msg` as multipart form data, saved to a temp file.
2. Whisper `base` model transcribes fast (task="translate") → streamed to client immediately.
3. Whisper `large-v3-turbo` transcribes again for accuracy → streamed as a correction.
4. Accurate text handed to the LangGraph agent.
5. Query Type Checker node classifies it as sale/expense/udhar.
6. The matching Validator node checks if all required fields are present.
7. If complete → the matching Query Generator node extracts a structured Pydantic object (item, amount, quantity, etc.) via `with_structured_output`.
8. If incomplete → Recommendation Engine generates catalog-grounded clarification suggestions instead.
9. Result streamed back over SSE; if complete, saved to MongoDB (`saleevents`/etc.) and a Node.js internal API is pinged to update daily aggregates.
10. Temp audio file deleted.

**What was the most challenging part of the project?**
Making the human-in-the-loop clarification loop feel like a real conversation on top of a request/response API — coordinating checkpointed state, the catalog-grounded recommender, and re-invoking the graph correctly across turns.

**What would happen if one component in the pipeline failed?**
Depends where: Whisper failure → no text to work with, request would need to fail gracefully (currently not explicitly retried — a gap). LLM API failure inside a node → unhandled exception would propagate up through the async generator and get caught by the generic `except stream_err` block in `api.py`, which yields an error event over SSE rather than crashing the connection silently. MongoDB failure → `save_transaction` would raise, again caught by the outer try/except and surfaced as an error event.

## Architecture

**Explain the architecture of VoiceTrace.**
Layered: (1) FastAPI HTTP/SSE layer handling uploads and streaming, (2) a dual Whisper STT layer, (3) a LangGraph agentic orchestration layer that does classification → validation → extraction/recommendation, (4) an async MongoDB persistence layer via Motor, (5) separate lightweight LangGraph agents (`next_day_agent`, `waste_agent`) for analytics-style features that read historical data and produce LLM-generated business advice.

**Why did you choose FastAPI?**
Native async support end-to-end (important since I'm juggling Whisper calls, LLM calls, and DB I/O concurrently), built-in Pydantic request validation, and it pairs naturally with the same Pydantic schemas I already use for LLM structured output — one validation mental model across the whole stack.

**Why did you choose MongoDB?**
Transaction records differ in shape by type (sale vs expense vs udhar have different required fields), and vendor catalogs are semi-structured — document storage avoids a sparse, nullable-heavy relational schema. Also pairs naturally with async Python via Motor, and I'm not doing heavy relational joins here.

**Why did you choose LangGraph?**
Because the control flow genuinely branches based on LLM output (transaction type, validation result) — it's not a straight pipeline. LangGraph gives me a shared typed state object, conditional routing as first-class graph edges, and checkpointed memory, all of which I'd otherwise be hand-rolling with a pile of if/else and manual state-passing.

**Why didn't you just use a single LLM prompt?**
A single mega-prompt trying to classify, validate, and extract at once would need to handle every transaction type's rules simultaneously — harder to get reliable, harder to debug when it's wrong (you can't tell if classification or extraction failed), and harder to extend. Splitting into focused nodes means each prompt has one job and I can trace exactly which step failed.

**How did different components communicate with each other?**
Within the graph, through the shared `State` TypedDict each node reads/writes. Whisper → agent communication is just passing the transcribed string into `main()`. Agent → frontend is SSE events. Agent → database is direct Motor calls in `tools/save_transaction.py` etc. There's also an internal HTTP call from the Python backend to a separate Node.js API (`/api/internal/update-daily`) to trigger daily aggregate updates after a sale is saved.

**What was the backend responsible for versus the frontend?**
Backend: audio ingestion, transcription, all AI orchestration, validation, persistence, and streaming progress updates. Frontend: capturing audio/text input, rendering the SSE progress stream, showing clarification suggestions and letting the vendor pick/respond.

## LangGraph / Agentic AI

**What is LangGraph?**
A library for building LLM applications as explicit graphs — nodes are functions (often LLM calls), edges define control flow (including conditional branching based on node output), and it comes with built-in state management and checkpointing for multi-turn workflows.

**What is an agentic workflow?**
One where the system makes a sequence of decisions — not just one LLM call in, one answer out — where the *path taken* depends on intermediate results (classify, then validate, then either extract or ask a question). My graph is an agentic workflow because the route through it isn't fixed; it's decided at runtime by earlier nodes' outputs.

**What is a StateGraph?**
LangGraph's core abstraction — a graph where you define a state schema, add nodes (functions that take state and return a partial state update), and wire edges (including conditional ones) between them. `StateGraph(State)` in my code, compiled into a runnable `graph`.

**What is the graph state?**
The shared data structure (a TypedDict) that flows through every node — each node can read any field and return updates that get merged in.

**What data did your graph state contain?**
`messages` (conversation history, using the `add_messages` reducer so it appends rather than overwrites), `recent_msg` (latest user text), `vendor_id`, `vendor_attributes` (catalog + financial insights fetched once at the start), and `original_input` (set once by the type-checker node).

**What are nodes in LangGraph?**
Functions registered on the graph — each takes the current state and returns a dict of updates. In my graph: Query Type Checker, Sale/Expense/Udhar Validator, Sale/Expense/Udhar Query Generator, Recommendation Engine.

**What are edges in LangGraph?**
Connections defining what runs next. Plain edges (`add_edge`) always go A→B. Conditional edges (`add_conditional_edges`) call a router function on the current state and pick the next node from a dict of possible destinations based on what it returns.

**What are conditional edges?**
Edges where the next node isn't fixed — a router function inspects the state (usually the last node's structured output) and returns a string key that maps to the actual next node. I use this twice: after the type checker (routes to the matching validator) and after each validator (routes to either the query generator or the recommendation engine).

**Explain the graph used in your project.**
`START → Query Type Checker → (conditional: sale/expense/udhar) → matching Validator → (conditional: correct/incorrect) → matching Query Generator or Recommendation Engine → END`. Three validators and three query generators are separate nodes with type-specific prompts and schemas.

**How did routing work in your graph?**
`route_by_type` reads the type-checker's structured JSON output and returns "sale"/"expense"/"udhar" (defaulting to "sale" if parsing fails). `route_query` reads a validator's `flag` boolean and returns "correct" or "incorrect". Both are registered as the routing function in `add_conditional_edges` with an explicit dict mapping return values to node names.

**How was transaction classification implemented?**
A dedicated node (`query_type_checker`) calls the LLM with `with_structured_output(TransactionType)` — a Pydantic model constraining output to exactly one of `sale`/`expense`/`udhar` — using a few-shot prompt with bilingual keyword examples (English + Hindi terms like "becha", "kharcha").

**What happens when validation fails?**
The validator's structured output has `flag=False` and a `missing` list of field names. Routing sends it to the Recommendation Engine, which uses the vendor's catalog to generate grounded clarification suggestions instead of guessing values or crashing.

**Why is LangGraph better than LangChain for this use case?**
LangChain's chain abstraction is mostly linear (A then B then C). My workflow needs branching based on intermediate LLM decisions and persistent multi-turn state — that's exactly what LangGraph's graph-with-conditional-edges-and-checkpointing model is built for, whereas plain LangChain chains would need custom control-flow code bolted on.

**Can LangGraph support loops?**
Yes — you can point an edge back to an earlier node to implement retry/iteration patterns. My current graph doesn't use an explicit loop-back edge; the "loop" (clarification → user reply → re-classification) happens by re-invoking the whole graph from `START` again with the same checkpointed `thread_id`, rather than looping within one execution. A cleaner version would use an actual `interrupt()`-based loop within a single graph run.

**Can LangGraph resume execution?**
Yes, natively, via `interrupt()`/`Command(resume=...)` — you can pause a node mid-execution, return control to the caller, and resume exactly there later. I don't use that mechanism currently; I approximate resumption by re-invoking the graph from `START` with the same `thread_id` so checkpointed message history carries over. It's honest to say that's a known simplification, not the "proper" LangGraph resume pattern — a good thing to bring up if asked about limitations.

**What is deterministic orchestration?**
Control flow that's explicit and predictable given the same inputs — as opposed to letting an LLM freely decide what to do next in an unconstrained agent loop. My graph is deterministic in structure: given a classification result, the routing logic always takes the same path. The *content* (what the LLM extracts) can vary, but *which nodes run* is fully explicit and traceable, which is valuable for a financial system where you want predictable behavior.

## Whisper / Speech-to-text

**What is Whisper?**
OpenAI's open-source automatic speech recognition model — an encoder-decoder transformer trained on a large amount of weakly-supervised multilingual audio-text data, supporting transcription, translation-to-English, and language identification from the same model via task tokens.

**What is the difference between Whisper Base and Whisper Turbo?**
Base is a small, fast model with lower accuracy. `large-v3-turbo` is a larger, much more accurate model that's slower per inference. I use Base for instant feedback and Turbo for the "real" accurate result.

**Why did you use a dual Whisper pipeline?**
To balance latency and accuracy — Base gives the user near-instant feedback that something is happening (avoids a dead-feeling UI during a multi-second wait), and Turbo streams in a correction once it's ready. It's an "optimistic UI" pattern.

**What is the advantage of running two transcription models?**
Perceived responsiveness without sacrificing final accuracy — you're not forced to choose between "fast but rough" and "slow but accurate," you get both, sequenced.

**Why not use only the Turbo model?**
Latency. Turbo alone would mean the user stares at a loading state for several seconds with zero feedback, which feels broken on a phone, mid-transaction, at a busy stall.

**What happens if the Turbo transcription fails or is empty?**
Fallback logic: if `accurate_text` is empty/whitespace after stripping, the code falls back to using `fast_text` (the Base model's output) instead of passing nothing downstream.

**Why translate speech to English internally?**
I run Whisper's `task="translate"`, which always outputs English regardless of spoken language. That gives me one consistent language to write extraction/classification prompts against, instead of branching prompt logic per vendor language. Vendor-facing text (like clarification suggestions) is generated separately in the vendor's stored native language.

**How did you process uploaded audio files?**
Received as multipart `UploadFile`, read into bytes, written to a uniquely-named temp file (`uuid`-based, to avoid collisions across concurrent requests), passed to Whisper by file path, then deleted in a `finally` block regardless of success/failure.

**Why did you use FFmpeg?**
Whisper's default audio loader shells out to `ffmpeg` to decode arbitrary input formats (m4a, etc.) into raw PCM. I patched the loader to use `imageio_ffmpeg`'s bundled ffmpeg binary so the app doesn't depend on a system-wide ffmpeg install — makes deployment more portable.

**What audio preprocessing did Whisper require?**
Mono channel, 16kHz sample rate, 16-bit PCM — my custom `load_audio` function runs ffmpeg with `-ac 1 -ar 16000 -f s16le` and converts the raw bytes into a normalized float32 numpy array, which is what Whisper's model expects as input.

## FastAPI and async

**What is FastAPI?**
A modern Python web framework built on Starlette and Pydantic, with native `async`/`await` support and automatic request/response validation from type hints.

**Why is FastAPI popular for AI applications?**
AI backends are I/O-heavy (LLM API calls, DB calls, sometimes streaming) — async support lets a single process handle many concurrent slow requests efficiently, and Pydantic integration matches naturally with LLM structured-output schemas.

**What is asynchronous programming?**
A concurrency model where a function can pause at an I/O-bound point (`await`) and let the event loop run other work, instead of blocking the whole thread until that I/O completes.

**Why did you use async/await?**
Because most of what my endpoints do is waiting — waiting on Whisper (CPU-bound, offloaded to a thread), waiting on the OpenAI API, waiting on MongoDB. Async lets the server keep serving other requests during those waits instead of one slow request stalling everyone.

**What is `asyncio.to_thread`?**
Runs a *synchronous, blocking* function in a separate worker thread and returns an awaitable, so it doesn't block the main async event loop. I use it for the two Whisper `.transcribe()` calls, which are CPU-bound and synchronous by nature.

**Why was `to_thread` necessary for Whisper?**
Whisper's `.transcribe()` is a synchronous, CPU-heavy call with no native async version. Calling it directly inside an `async def` route would block the entire event loop for the whole transcription — freezing every other concurrent request on that server process. `to_thread` moves that blocking work off the event loop.

**What is a coroutine?**
A function defined with `async def` that returns a coroutine object when called, which needs to be awaited (or scheduled) to actually run — it can suspend and resume around `await` points instead of running start-to-finish synchronously.

**What happens if you run blocking code directly in FastAPI?**
It stalls the single-threaded event loop — every other concurrent request being served by that worker is blocked until the synchronous call finishes, killing the concurrency benefit async is supposed to give you. This is actually a real gap I have in `next_day_agent.py`/`waste_agent.py`, where `llm.invoke()` is called directly inside `async def` node functions without `to_thread` — worth mentioning proactively if asked about weaknesses.

**What is concurrency?**
Structuring a program to make progress on multiple tasks by interleaving them (e.g., waiting on one while working on another) — doesn't necessarily mean literal simultaneous execution.

**What is the difference between concurrency and parallelism?**
Concurrency is about *managing* multiple tasks at once (can be on one core, via interleaving I/O waits — this is what `async`/`await` gives me). Parallelism is *literally* executing multiple tasks at the same time on multiple cores/threads (this is what `to_thread` gives me for the CPU-bound Whisper calls — actual parallel execution on a separate thread).

## SSE (Server-Sent Events)

**What is SSE?**
A simple, one-directional streaming protocol over plain HTTP — the server keeps a connection open and pushes a sequence of `data: ...\n\n` formatted text events, which the client reads incrementally instead of waiting for one full response.

**Why did you use SSE instead of a normal REST response?**
The pipeline (transcribe → refine → classify → validate → extract/save) takes multiple seconds across several stages. A normal request/response would leave the user staring at a blank loading state the whole time. SSE lets me push a progress update after each stage so the UI always shows what's currently happening.

**What was streamed to the frontend?**
Status strings at each pipeline stage ("Analyzing audio...", fast transcription text, refined transcription text, "AI Agent processing..."), then the final result — either a completed transaction record or a clarification-needed event with suggestions, and a final "saved" event with the inserted DB id.

**How does SSE work internally?**
FastAPI's `StreamingResponse` wraps an `async def` generator; each `yield` sends one chunk over the open HTTP connection immediately, formatted as `data: {json}\n\n`, with `media_type="text/event-stream"`. The browser's `EventSource` (or a manual fetch-stream reader) parses each event as it arrives.

**SSE vs WebSockets.**
SSE is one-directional (server→client only), built on plain HTTP, and simpler to implement/reconnect. WebSockets are full-duplex (both directions), need a protocol upgrade, and are better suited for interactive back-and-forth like chat. My use case is purely "push progress updates," so SSE is the simpler, sufficient choice.

**Why was SSE sufficient for your application?**
Because the client never needs to push data back over the *same* open stream — clarification replies go through a fresh request (`/api/recommend_msg`), not through the SSE channel. The SSE channel's only job is reporting progress on a task already in flight.

**What happens if the client disconnects during streaming?**
Currently not explicitly handled — the generator would keep yielding to a closed connection until FastAPI/Starlette detects the disconnect and stops iterating. A production hardening step would be catching `asyncio.CancelledError` in the generator to clean up temp files or in-flight state properly, and possibly persisting partial progress so the pipeline doesn't have to fully restart on reconnect.
