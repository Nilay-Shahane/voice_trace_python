## Transaction validation and routing

### Explain your transaction type checker.

The transaction type checker is the **entry node** of my LangGraph workflow. It receives the transcribed text and uses an LLM with **structured output** to classify it into exactly one of three types: **sale**, **expense**, or **udhar**. The output is constrained by a Pydantic schema so the router always receives a predictable value.

### Explain the sale validator.

The sale validator checks whether a sale transaction contains all required information before it can be stored. It verifies that the message clearly indicates a sale and that fields such as **item**, **amount**, and **quantity** (when applicable) are present. It does not extract values; it only checks completeness.

### Explain the expense validator.

The expense validator verifies that the user is describing a spending event and checks that **amount** and **expense category** are present. If either is missing, it returns a structured list of missing fields.

### Explain the udhar validator.

The udhar validator handles credit and debt transactions. It checks whether the direction of the transaction is clear (given or received), whether the **amount** is present, and whether a **person name** is explicitly mentioned.

### Why separate validators for different transaction types?

Each transaction type has different business rules. A sale requires item and quantity, an expense requires an expense category, and udhar requires a person name and direction. Separate validators keep prompts simpler and improve accuracy.

### What fields are required for a sale?

* Transaction type
* Item
* Amount
* Quantity (for countable goods)

### What fields are required for an expense?

* Transaction type
* Amount
* Expense category

### What fields are required for udhar?

* Transaction direction (given or received)
* Amount
* Person name

### How did routing decisions work?

Routing was implemented using **LangGraph conditional edges**. After the type checker, the graph routes to the corresponding validator. After validation, it routes either to the appropriate query generator or to the recommendation engine depending on whether required fields are missing.

### What happens when required fields are missing?

The validator returns `flag=False` and a list of missing fields. The graph routes to the **Recommendation Engine**, which generates clarification suggestions grounded in the vendor's catalog instead of guessing values.

## Recommendation engine

### What does the recommendation engine do?

It generates **catalog-aware clarification suggestions** when a transaction is incomplete. Instead of asking a generic question, it proposes realistic completions using the vendor's actual inventory and pricing information.

### How did it generate clarification suggestions?

It received the original user message, the list of missing fields, and the vendor's item catalog from the graph state. The LLM prompt instructed it to generate **1–3 short conversational suggestions** using only items that actually exist in the catalog.

### How did vendor catalog data help?

It prevented the model from inventing products that the vendor does not sell. For example, if the vendor only sells samosas and chai, the recommendation engine will not suggest pizza or sandwiches.

### Why not ask a generic clarification question?

Catalog-grounded suggestions are faster and easier for users. Instead of asking “What item did you sell?”, the system can ask “Did you mean you sold 2 samosas for 20 rupees?”, which reduces typing and improves usability.

### How did you keep suggestions realistic?

The prompt explicitly restricted the model to **items in the catalog**, practical quantities, and known prices. This grounding significantly reduced hallucinated recommendations.

### Give an example recommendation.

If the user says “I sold something for 20 rupees,” the engine might respond:

* “Did you mean you sold 2 samosas for 20 rupees?”
* “Did you mean you sold 1 chai for 20 rupees?”

## Database

### Why MongoDB instead of SQL?

Transaction records vary by type. Sales, expenses, and udhar entries have different fields, so a document database is a natural fit. MongoDB also integrates well with Python and asynchronous I/O.

### What collections did you use?

The project primarily uses collections such as:

* `saleevents`
* `dailyrecords`
* `recommendations`
* `vendors`

### How were transactions stored?

After successful extraction, the structured transaction object was converted into a MongoDB document and inserted asynchronously. Sales were also forwarded to a Node.js service that updated daily aggregate records.

### What is Motor?

Motor is the **asynchronous MongoDB driver for Python**. It allows MongoDB operations to be awaited inside FastAPI endpoints without blocking the event loop.

### Why use Motor instead of PyMongo?

PyMongo is synchronous, while Motor is async. Since FastAPI is asynchronous, Motor keeps database operations non-blocking and allows better concurrency.

### What is BSON?

BSON is **Binary JSON**, the internal storage format used by MongoDB. It supports additional data types such as ObjectId and datetime.

### Why use ObjectId?

ObjectId provides a unique identifier for each MongoDB document and is the standard primary key type used by MongoDB.

### How did you serialize MongoDB data?

When returning historical records to LLM prompts, I converted **ObjectId values to strings** and **datetime values to ISO-formatted strings** so they could be safely serialized into JSON.

## API design

### Explain the `/api/speech_msg` endpoint.

This endpoint receives audio and metadata, runs the dual Whisper transcription pipeline, streams progress updates using SSE, invokes the LangGraph agent, and finally stores completed transactions in MongoDB.

### Explain the `/api/recommend_msg` endpoint.

This endpoint handles follow-up clarification responses. It deletes any stale recommendation state, re-invokes the LangGraph workflow with the user's clarification, and streams the updated processing status.

### Explain the next-day suggestion endpoint.

It runs a separate LangGraph workflow that loads the vendor's recent sales history, summarizes trends, and asks the LLM to generate **next-day stock preparation suggestions** in the vendor's preferred language.

### Explain the waste insight endpoint.

It analyzes historical waste records and uses an LLM to generate **actionable waste-reduction recommendations**, such as reducing preparation quantities for frequently wasted items.

### Why did you separate these APIs?

Each endpoint has a different responsibility: transaction logging, clarification handling, inventory planning, and waste analytics. Separating them keeps the backend modular and easier to maintain.

### What HTTP methods did you use?

Primarily **POST** endpoints, because the requests contain audio files, metadata, or user-specific payloads that create or process resources.

### How did you handle errors?

Each endpoint is wrapped in `try/except` blocks. Streaming errors are caught inside the async generator and returned as SSE error events instead of crashing the connection.

## Concurrency and performance

### How did you reduce perceived latency?

I used a **dual Whisper pipeline**. The Base model produced a quick transcript that was streamed immediately, while the Turbo model produced a more accurate transcript later.

### What was the slowest component?

The slowest components were **Whisper Turbo transcription** and **LLM API calls**, because both involve significant computation or network latency.

### How would you optimize transcription speed?

* Run Whisper on a GPU
* Use a smaller model when acceptable
* Batch requests
* Cache repeated audio
* Move transcription to a dedicated inference service

### How would you handle 10,000 concurrent vendors?

I would separate the system into independent services: API gateway, transcription workers, LangGraph workers, and database workers. Requests would be queued and processed asynchronously.

### What would become the bottleneck?

The largest bottlenecks would likely be **Whisper inference**, **LLM API throughput**, and **database write capacity**.

### How would you horizontally scale FastAPI?

Run multiple FastAPI worker processes behind a load balancer and make the application stateless so any worker can handle any request.

### Would you use a message queue?

Yes. For large-scale deployments I would place audio-processing requests into a queue so transcription and LLM processing can be handled by background workers.

### Redis vs Kafka for this project.

Redis is better for **low-latency task queues and caching**, while Kafka is better for **high-throughput event streaming and durable messaging**. For VoiceTrace, I would start with **Redis**.

### Where would caching help?

* Vendor catalog lookups
* Frequently accessed vendor metadata
* Repeated LLM prompt templates
* Historical analytics results

## Failure handling

### What happens if Whisper fails?

The request cannot be transcribed, so the system should return an error and avoid creating any transaction. A production version should also implement retries and logging.

### What happens if the LLM API fails?

The exception propagates through the graph and is caught by the FastAPI streaming layer, which returns an SSE error event to the client.

### What happens if MongoDB is unavailable?

Transaction persistence fails, and the backend should return an error rather than pretending the transaction was saved successfully.

### What happens if SSE streaming fails?

The client stops receiving progress updates. The backend should detect disconnects and clean up temporary resources.

### How would you add retries?

I would add exponential backoff retries around **LLM API calls**, **database writes**, and **network requests**, while ensuring operations remain idempotent.

### How would you make the pipeline idempotent?

Attach a unique transaction ID or request ID to each operation so repeated requests do not create duplicate database entries.

### How would you avoid duplicate transactions?

Use unique transaction identifiers, deduplicate repeated submissions, and make database writes conditional on transaction IDs.

## Machine learning theory connected to the project

### Is Whisper supervised or self-supervised?

Whisper is primarily trained using **supervised learning** on large speech–text datasets, although it also benefits from large-scale representation learning.

### What type of model is Whisper?

Whisper is a **transformer-based encoder-decoder speech recognition model**.

### What type of model is GPT?

GPT is a **decoder-only transformer language model**.

### What is a transformer?

A transformer is a neural network architecture that uses **self-attention** to process relationships between tokens in parallel rather than sequentially.

### What is attention?

Attention allows the model to focus on the most relevant parts of the input when generating each output token.

### Why are transformers good for language tasks?

Because they capture long-range dependencies efficiently and can process entire sequences in parallel during training.

### What is tokenization?

Tokenization converts text into smaller units called **tokens**, which are the units processed by the model.

### What is an embedding?

An embedding is a dense numerical vector that represents the semantic meaning of a token or piece of text.

### What is a context window?

The context window is the maximum amount of text the model can consider at one time when generating a response.

### What is inference?

Inference is the process of using a trained model to generate predictions or outputs for new input data.

Machine learning is used in **speech recognition**, **transaction classification**, **structured information extraction**, and **recommendation generation**.

## Security

### How would you secure this API?

Use HTTPS, authentication tokens, request validation, rate limiting, input sanitization, and secret management through environment variables.

### How would authentication work?

Each vendor would authenticate using a secure token or JWT, and every request would be associated with an authenticated vendor ID.

### How would you prevent abuse?

Implement **rate limiting**, request quotas, authentication, logging, anomaly detection, and possibly CAPTCHA for suspicious traffic.

### How would you protect vendor financial data?

Encrypt data in transit and at rest, restrict database permissions, authenticate every request, and avoid exposing internal identifiers to clients.

### How would you encrypt sensitive data?

Use **TLS/HTTPS** for data in transit and database-level encryption or field-level encryption for sensitive stored information.

### How would you handle API rate limiting?

Use middleware or an API gateway to limit requests per user or per IP address and return appropriate **429 Too Many Requests** responses when limits are exceeded.
